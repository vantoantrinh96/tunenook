# In-app updates (Sparkle)

## Intent

Today the only way to get a new TuneNook is to open GitHub Releases, download the `.dmg`, drag the app to Applications and clear quarantine by hand. The owner wants TuneNook to notice new versions by itself, offer a **Check for Updates…** action, and install the update in place: one click, then the app relaunches.

The repo was made public on 2026-11-18, so release assets are downloadable without auth. `main` is protected by a ruleset. PR #13 (`ci/release-deploy-key`) makes the Release workflow push its bump commit with the `RELEASE_DEPLOY_KEY` deploy key. **PR #13 must be merged before this work starts.** Branch from `main` after that merge, because this work edits the same `release.yml` and merging it fires a release.

## Goals

- Scheduled background checks, on by default, once a day.
- **Check for Updates…** in the menu bar popover footer and in Settings → General.
- When an update is found: a dialog with the version, release notes and **Install and Relaunch**. Accepting downloads, verifies, replaces the app in place and relaunches it.
- Settings → General: "Check for updates automatically" toggle and "Download and install updates automatically" toggle (off by default), plus the current version.
- Every update is cryptographically verified before it's installed.
- Release CI produces everything the updater needs with no manual steps.

## Non-goals

- Delta updates, beta/pre-release channels, Intel builds.
- Notarization or a Developer ID certificate (the app stays ad-hoc signed).
- Updating versions that shipped before this feature: they have no updater, so the owner installs the first Sparkle-enabled release by hand once.

## Anti-goals

- Interrupting a focus session: a *scheduled* check must not pop a window over the user's work while focus is running. (A manual check always shows its result immediately.)
- Losing a timer session to an update. Relaunching throws away `TimerEngine`'s in-memory state (the current phase and the long-break cycle position), and nothing about it is saved.
- Installing anything that isn't signed with the project's EdDSA key.
- Breaking the existing release outputs (`.dmg`, `.zip`, `.sha256`) or the bump/tag flow.

## Constraints (from the project)

- macOS 14+, Apple silicon only, Swift 6, project generated by XcodeGen from `project.yml` (edit that, never the `.xcodeproj`, `Info.plist` or entitlements).
- App Sandbox is on with `network.client`; Hardened Runtime is on; code signing is ad-hoc (`CODE_SIGN_IDENTITY: "-"`, no team).
- `LSUIElement` menu bar app: no Dock icon, no main menu, so "Check for Updates…" lives in the popover and Settings.
- Versioning: `scripts/release.sh bump` raises `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` (integer, +1 each release). The build number is what Sparkle compares, so it must keep increasing.
- Releases are created by `.github/workflows/release.yml` (`build` job on `macos-15`) via `gh release create`.

## Approaches considered

1. **Sparkle 2** (chosen). Standard macOS updater: scheduled checks, update UI, EdDSA verification, in-place install and relaunch, quarantine handling, and supports sandboxed apps through its XPC installer service. Costs a dependency and sandbox/CI setup.
2. **Home-grown updater** (GitHub API + download + replace). Checking is easy, but a sandboxed app cannot replace itself in `/Applications`; making that work means writing an out-of-sandbox helper, i.e. re-implementing Sparkle's hardest part.
3. **Notify only, open the release page.** Trivial, but the user still downloads and drags by hand, which is exactly what we're removing.

The owner picked Sparkle.

## Design

### Dependency

Sparkle 2 (latest 2.x) via Swift Package Manager in `project.yml` (`packages:` + target dependency), embedded and signed with the app.

### Feed and keys

- **Feed URL:** `https://github.com/vantoantrinh96/tunenook/releases/latest/download/appcast.xml`. GitHub redirects to the newest release's asset, so no extra hosting is needed.
- **Signing:** an EdDSA key pair generated once with Sparkle's `generate_keys`. Public key goes in Info.plist (`SUPublicEDKey`) via `project.yml`; private key is stored only as the repo secret `SPARKLE_ED_PRIVATE_KEY` (and the owner may keep a backup; losing it means users can't take updates without a manual reinstall).
- **Update archive:** the existing `TuneNook-<version>.zip` (made with `ditto -c -k --keepParent`, which Sparkle handles). The `.dmg` stays for first installs.

### Info.plist / entitlements (via `project.yml`)

- `SUFeedURL`, `SUPublicEDKey`, `SUEnableAutomaticChecks = YES` (skips Sparkle's "check automatically?" prompt; the owner wants it on), `SUScheduledCheckInterval = 86400`, `SUEnableInstallerLauncherService = YES` (required in the sandbox).
- Entitlement `com.apple.security.temporary-exception.mach-lookup.global-name`: `$(PRODUCT_BUNDLE_IDENTIFIER)-spks` and `$(PRODUCT_BUNDLE_IDENTIFIER)-spki`.
- The downloader XPC service isn't needed: the app already has `network.client`.

### App code

- A small `UpdaterController` (`@Observable`, `@MainActor`) in `TuneNook/System/` owning `SPUStandardUpdaterController`, exposing `canCheckForUpdates`, `checkForUpdates()`, and bindings for `automaticallyChecksForUpdates` / `automaticallyDownloadsUpdates`. Created in `TuneNookApp.init` and passed through `.environment` like the other services.
- Popover footer (`MenuBarView.footer`): a "Check for Updates…" control next to Settings/Quit (an icon button with a tooltip matches the existing footer style).
- Settings → General: a new "Updates" section with the two toggles, the current version (`CFBundleShortVersionString` + build), and a "Check Now" button.
- **Never relaunch over an active session (owner's decision):** if the user accepts an update while a session is active (any phase, running or paused, i.e. anything other than idle), don't relaunch. The update installs when the app quits, whether the user picks Quit, logs out or shuts down. Tell the user plainly, e.g. "TuneNook X will be installed when you quit TuneNook." With no active session, Install and Relaunch behaves normally. Use Sparkle's `SPUUpdaterDelegate` postpone and install-on-quit hooks (`updater(_:shouldPostponeRelaunchForUpdate:untilInvokingBlock:)` and related). The builder confirms the exact mechanism in the end-to-end test. The same rule applies to automatically downloaded updates.
- **No interruptions during focus:** implement Sparkle's gentle scheduled reminders (`SPUStandardUserDriverDelegate.supportsGentleScheduledUpdateReminders` and `standardUserDriverShouldHandleShowingScheduledUpdate`). Here "focus" means the focus phase, running or paused. Breaks don't count. When a scheduled check finds an update during focus, don't show the window. Post a regular notification ("TuneNook X is available"), then show the update window **automatically as soon as the focus phase ends**, or earlier if the user opens the notification or picks Check for Updates…. The update still surfaces when notifications are denied or ignored. Outside focus, Sparkle shows its window normally. Manual checks are never deferred. *(Claude's call: showing it at focus end means nothing depends on notification permission, and a break is a good moment to offer it.)*

### Release CI (`build` job)

After packaging, before `gh release create`:

The appcast embeds the release notes, so the release must exist first. Order: `gh release create` as today, then:

1. Download a pinned Sparkle release tarball (the same version as the SPM package) and verify its SHA-256, to get `bin/sign_update`.
2. Sign the zip: `sign_update --ed-key-file - TuneNook-$VERSION.zip` with the key from `SPARKLE_ED_PRIVATE_KEY` on stdin, never on disk or in logs.
3. Write `appcast.xml` with one `<item>`: `sparkle:version` = `CURRENT_PROJECT_VERSION`, `sparkle:shortVersionString` = `$VERSION`, `sparkle:minimumSystemVersion` = `14.0`, a `<description>` holding the generated release notes (read back with `gh release view --json body`; use Sparkle's markdown or plain-text description format if the pinned version supports it, else convert to minimal HTML), a `<link>` to the GitHub release page, and an `<enclosure>` whose URL is `https://github.com/<repo>/releases/download/v$VERSION/TuneNook-$VERSION.zip` with the signature and length from step 2.
4. Upload `appcast.xml` to the release with `gh release upload`. For a few seconds after the release is created, `latest/download/appcast.xml` returns 404. Sparkle treats that as a failed check and retries on the next schedule, which is acceptable. *(Claude's call: the GitHub release page itself would render with GitHub's full site header inside the small notes area of the dialog.)*

Only the newest item is needed, because the feed URL always resolves to the newest release.

### Signing and Hardened Runtime

The app is ad-hoc signed with Hardened Runtime on. Library validation only allows loading code from the same Team ID, and ad-hoc signatures have none, so the embedded `Sparkle.framework` may fail to load. The builder must check this in a Release build. If it fails, add `com.apple.security.cs.disable-library-validation` (keep Hardened Runtime) and record why in `project.yml`. Sparkle's EdDSA check is what secures updates here, since Apple's code-signing identity check can't help with ad-hoc signing.

## Testing

- Unit-test what's ours: the "defer while focus is running / show when focus ends" logic, the "postpone relaunch while a session is active" decision and the appcast generation (if it's a script, test it the way `release.sh` is used, or with a small shell test).
- Manual end-to-end check before merging: build an older version locally (e.g. bump the build number down), serve a locally signed `appcast.xml` + zip (temporary `SUFeedURL` override through `defaults write <bundle id> SUFeedURL …`), and confirm check → dialog → install → relaunch into the new version, inside the sandbox. Also check the active-session path (accept during focus → no relaunch → quit → the new version is installed) and a scheduled check during focus (no window → it appears when focus ends).

## Left to the builder

- Exact Sparkle version (latest stable 2.x at build time, pinned in both SPM and CI).
- Footer icon and Settings layout details, matching the existing style.
- Whether the appcast is written by an inline heredoc in `release.yml` or by a `scripts/make-appcast.sh` (prefer the script, for testability).

## Setup the owner does once

- Generate the EdDSA key pair and add `SPARKLE_ED_PRIVATE_KEY` (Claude can do this with `generate_keys -x` into the scratchpad, `gh secret set` and then delete the local file).
- Install the first Sparkle-enabled release by hand. After that, updates come through the app.
