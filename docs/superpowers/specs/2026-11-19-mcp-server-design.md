# MCP server

## Intent

The owner wants AI agents (Claude Code and similar MCP clients) to work with TuneNook's data: manage topics and tasks, read and change settings, and look at focus history, without opening the app's windows. Typical use: "add these five tasks to the Thesis topic", "mark X done", "set focus to 50 minutes", "how much did I focus this week".

This is the first of two MCP features. TuneNook as an MCP **client** (pulling tasks from Linear, Notion and so on) comes later and is out of scope here.

## Goals

- TuneNook runs an MCP server that a local MCP client can connect to.
- Tools to list, create, update and delete **topics** and **tasks**.
- Tools to read and change **settings**.
- Tools to **view history**: past sessions and progress. Read-only.
- Changes made by an agent show up in the open app immediately, with no relaunch.
- The server is off until the user turns it on in Settings, and Settings gives the user everything needed to connect a client.

## Non-goals

- Controlling the timer (start, pause, stop, skip, pick the current task).
- Controlling the radio.
- Creating, editing or deleting focus sessions.
- Settings tied to the machine: global shortcut, open at login, update preferences, selected menu bar icon.
- MCP client features, MCP resources, prompts, sampling.
- A stdio helper binary, and access from other machines.
- Working while TuneNook is not running.

## Anti-goals

- An agent ending or disturbing a focus session that is running.
- Any other process on the Mac, or any web page, reading or changing the data without the token.
- The server listening on anything but loopback.
- Agent edits corrupting the store or leaving the UI showing stale data.
- Rewriting whether past days met their goal (`GoalHistory` already protects this; go through `GoalStore`).

## Constraints (from the project)

- macOS 14+, Apple silicon, Swift 6, project generated by XcodeGen from `project.yml` (edit that, never the `.xcodeproj`, `Info.plist` or entitlements).
- App Sandbox is on with only `network.client`; Hardened Runtime on; ad-hoc signing with no team. Ad-hoc signatures change every build, so the Keychain would prompt after each update.
- Data: SwiftData models `Topic`, `TodoTask`, `FocusSession` in one `ModelContainer`, used from `mainContext`. Models have no ID field of their own.
- Settings live in `UserDefaults.standard`: `TimerSettings`, `AwayPolicy`, `MusicRules`, `CelebrationLevel` read keys directly and the Settings UI binds with `@AppStorage`; `GoalStore` keeps the goal history and day start hour in memory and writes them through.
- `TimerEngine.currentTask` holds a `TodoTask`. The UI abandons the running session when its task or topic is deleted (`TaskListView.delete`, `TopicSidebar.delete`).
- The MCP Swift SDK (`modelcontextprotocol/swift-sdk`, 0.12.1) declares swift-tools-version 6.1, so it needs Xcode 16.3 or newer locally and in CI (`macos-15`). The README says Xcode 16+; update it.
- CI runs Gitleaks and Semgrep; no token or key may be committed.
- `main` is far behind the current stack. Branch from `feat/auto-update` (my call), or from `main` if that stack has merged by then.

## Approaches considered

1. **HTTP server inside the app** (chosen). The app listens on `127.0.0.1` and speaks MCP Streamable HTTP. It shares the app's `ModelContainer`, `UserDefaults` and `GoalStore`, so the UI updates live and there's one writer. Costs the `network.server` sandbox entitlement and a token. The app must be running. Claude Code, Cursor and VS Code connect by URL; Claude Desktop needs the `mcp-remote` bridge.
2. **Bundled stdio helper that opens the store itself.** Works with every client and with the app closed. But two processes write one SwiftData store, the running app doesn't see the changes until relaunch, macOS asks the user to allow access to another app's container, and settings sit in the sandboxed defaults. Rejected: stale UI and risk to the data.
3. **Bundled stdio helper that forwards to the running app.** Works with every client and keeps one writer, but needs everything in approach 1 plus a second target. Worth adding later only if Claude Desktop becomes the main client; the tools from approach 1 would be reused unchanged.

The owner was shown these three with approach 1 recommended, and replied by adding history to the scope without objecting. Approach 1 is taken as picked; this is confirmed when the owner approves this document.

## Design

### Pieces

- **`MCPServerController`** (`@MainActor @Observable`, in `TuneNook/MCP/`): owns the on/off state, the port, the token, the listener and the current status (off, running, failed with a reason). Created in `TuneNookApp.init`, put in the environment for Settings. Starts at launch if enabled.
- **HTTP listener**: `Network.framework` `NWListener` bound to IPv4 loopback only, feeding requests to the SDK's HTTP server transport. Which of `StatelessHTTPServerTransport` / `StatefulHTTPServerTransport` to use is left to the builder; nothing here needs server-initiated messages, so stateless is enough if the target clients accept it.
- **Tool layer**: plain types that take a `ModelContext`, `UserDefaults`, `GoalStore` and a "which task is busy" closure, and return `Codable` results. No dependency on the SDK or the network, so it's unit-tested directly with an in-memory container. The MCP layer on top only maps tool names and JSON arguments to these calls.
- All data access happens on the main actor through `container.mainContext`, with a `save()` after each write, so SwiftUI `@Query` views refresh by themselves.

### Security

- **Off by default.** A toggle in Settings turns it on.
- **Loopback only.** Never bind a wildcard address.
- **Bearer token.** Every request needs `Authorization: Bearer <token>`; otherwise 401. The token is 32 random bytes, generated the first time the server is enabled, stored in `UserDefaults` (my call: Keychain would prompt after every update because of ad-hoc signing, and the sandbox container already keeps other sandboxed apps out). Compare in constant time. **Regenerate** in Settings replaces it and drops existing clients.
- **Host and Origin checks** to block DNS rebinding from a browser: reject requests whose `Host` isn't `127.0.0.1:<port>` or `localhost:<port>`, and any request with an `Origin` header that isn't loopback. The SDK ships `HTTPRequestValidation`; use it if it covers this.
- The token never appears in logs.

### Sandbox

Add `com.apple.security.network.server: true` to the entitlements in `project.yml`.

### Port

Fixed default `47821` (my call), editable in Settings. If the port is taken, the server doesn't start and Settings shows why. No automatic fallback to another port, because the client's saved URL would silently stop matching.

### Settings UI

A new **Agents** tab in `SettingsView`:

```
│ MCP server                                          │
│   Let AI agents manage TuneNook      [ on/off ]     │
│   Status      ● Running on 127.0.0.1:47821          │
│   Port        [ 47821 ]                             │
│   Token       ••••••••••••  [Copy] [Regenerate]     │
│                                                     │
│ Connect a client                                    │
│   Claude Code  [Copy command]                       │

│                                                     │

```

- "Copy command" yields `claude mcp add --transport http tunenook http://127.0.0.1:<port>/mcp --header "Authorization: Bearer <token>"`.
- "Copy config" yields the generic `mcpServers` JSON with `url` and `headers`.
- Regenerate asks for confirmation.

### IDs

Tools refer to topics and tasks by an opaque string `id`. Models have no ID field, so derive it from `PersistentIdentifier` (it's `Codable`; encode and base64url it) rather than adding a column and a migration (my call; the builder may add a stored UUID instead if the encoded identifier proves unstable across launches, which must be tested). An unknown or malformed id returns a tool error, not a crash.

### Tools

All results are JSON text. Dates are ISO 8601 with time zone. Errors come back as MCP tool errors (`isError: true`) with a plain sentence the agent can act on.

**Topics**

| Tool | Arguments | Notes |
|---|---|---|
| `list_topics` | none | id, name, color, deadline, open and done task counts |
| `create_topic` | `name`, `color?`, `deadline?` | `color` must be one of `Topic.palette`; default is the first |
| `update_topic` | `id`, `name?`, `color?`, `deadline?` | `deadline: null` clears it |
| `delete_topic` | `id` | Deletes its tasks too (existing cascade); session history is kept |

**Tasks**

| Tool | Arguments | Notes |
|---|---|---|
| `list_tasks` | `topic_id?`, `status?` (`open`, `done`, `all`; default `open`) | id, title, topic, estimate, actual sessions, done, created, completed |
| `create_task` | `title`, `topic_id`, `estimated_sessions?` (default 1) | `topic_id` is required (my call): the app only shows tasks through their topic, so a task without one would be invisible to the user |
| `update_task` | `id`, `title?`, `estimated_sessions?`, `topic_id?`, `done?` | `done` goes through `TodoTask.setDone` so `completedAt` stays right. `topic_id` moves the task; it can't be cleared |
| `delete_task` | `id` | Its sessions stay, detached (existing nullify rule) |

Names are trimmed and must not be empty. Estimates use the same range the UI allows.

**Busy task rule (my call).** If a focus session is active on a task (`engine.isTaskLocked`), `delete_task` on it and `delete_topic` on its topic are refused with an error saying a focus session is running on it. The UI abandons the session in that case; an agent must not be able to. Editing that task (title, estimate, topic, done) is allowed.

**Selected but not busy (my call).** `engine.currentTask` also stays set while the timer is idle or on a break. Deleting that task, or its topic, is allowed, and the tool clears `engine.currentTask` first, exactly as the UI does, so the engine never holds a deleted model. This is cleanup, not timer control: no session is running on the task, so nothing is interrupted. The tool layer therefore takes two closures from the engine: "is this task busy" and "deselect this task if selected".

**Settings**

| Tool | Arguments |
|---|---|
| `get_settings` | none |
| `update_settings` | any subset of the fields below |

| Field | Backed by |
|---|---|
| `focus_minutes`, `short_break_minutes`, `long_break_minutes`, `long_break_interval`, `auto_start_breaks`, `auto_start_focus` | `TimerSettings.Key` |
| `daily_goal` `{kind: minutes\|sessions, target}` | `GoalStore.setGoal` |
| `day_start_hour` (read-only) | `GoalStore.dayStartHour`. Returned by `get_settings`, rejected by `update_settings` (my call): changing it re-buckets every past session into different days, which can flip past goal days and streaks. The user changes it in Settings |
| `break_music` (`keepPlaying`, `lowerVolume`, `stop`, `switchStation`), `break_station_id` | `MusicRules.Key` |
| `celebrations` (`off`, `milestones`, `everySession`) | `CelebrationLevel.key` |
| `pause_on_lock`, `idle_pause_minutes` | `AwayPolicy.Key` |

Each value is validated against the same limits and choices the Settings UI offers (`AwayPolicy.idleChoices`, the steppers' ranges, station ids from `stations.json`). One invalid field rejects the whole call and changes nothing. `get_settings` also returns the allowed values for the enum fields and the list of stations, so the agent doesn't guess. Writes go through `UserDefaults.standard` and `GoalStore`, which the existing `@AppStorage` and `@Observable` bindings already watch.

**History** (read-only)

| Tool | Arguments | Returns |
|---|---|---|
| `list_sessions` | `from?`, `to?` (default: last 7 days), `topic_id?`, `task_id?`, `kind?`, `completed_only?`, `limit?` (default 100, max 500) | Sessions newest first: kind, start, end, active minutes, completed, task and topic; plus whether more exist |
| `get_progress` | `days?` (default 7, max 366) | Today's total against the goal, current and longest streak, freezes, and focus minutes and sessions per focus day |

`get_progress` reuses `FocusProgress` / `FocusStats` and `FocusCalendar`, so day boundaries and streaks match the Progress page. The split into these two tools is my call from "view history".

### Lifecycle

- Enabled at launch: start listening after the container is ready.
- Toggle off, port change or token regenerate: stop the listener, close open connections, restart if still enabled.
- App quit: the listener goes with the process; nothing to persist.
- A failure to start never blocks or crashes the app; it only shows in Settings.

### Tests

- Tool layer against an in-memory `ModelContainer` and a throwaway `UserDefaults` suite: each tool's happy path, validation failures, unknown ids, the busy-task rule, cascade and nullify on delete, all-or-nothing `update_settings`, goal changes not rewriting past days, id round-trip.
- Request gate as a pure function: token missing or wrong, bad `Host`, foreign `Origin`.
- One end-to-end check through the SDK's `InMemoryTransport`: `tools/list` and one `tools/call`.
- The listener and Settings tab are checked by hand with Claude Code connected to a debug build.
